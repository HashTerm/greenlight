# Callbacks

Greenlight notifies your agent when prompts are answered or when inbound
messages arrive on `MESSAGE` channels.

## Prompt answer callbacks (signed)

Delivered to the prompt's `callback_url` as `POST` with:

```http
X-Signature: sha256=<hmac-sha256-hex-of-raw-body>
```

Secret: `CALLBACK_SIGNING_SECRET`. Retries up to 5 times with exponential backoff.

### Payload

```json
{
  "prompt_id": "#2",
  "channel_id": "telegram-prompts",
  "correlation_id": "deploy-42",
  "callback_data": {
    "build_id": 9182,
    "pipeline": "prod"
  },
  "text": "Approve production deploy?",
  "answer": {
    "type": "option",
    "value": "Approve",
    "user_id": null,
    "username": null
  },
  "answered_at": "2026-07-25T12:00:00.000Z"
}
```

| Field            | Notes                                                                   |
| ---------------- | ----------------------------------------------------------------------- |
| `prompt_id`      | Per-channel id (`#n`)                                                   |
| `channel_id`     | Greenlight PROMPT channel id                                            |
| `correlation_id` | Short label from create (optional)                                      |
| `callback_data`  | JSON object or array from create (optional), echoed for workflow resume |

### Outbound headers (`callback_headers`)

On create (prompt or MESSAGE channel), optional `callback_headers` sends HTTP
headers on the outbound POST — for example `Authorization: Bearer …` or
`X-Api-Key`. Greenlight still sets `Content-Type` and `X-Signature` on prompt
callbacks; integrator headers cannot override those.

Header values are **never** returned by the API (`callback_headers_configured`
on GET). Do not put Bearer tokens in `callback_data` or URL query strings.

Verify ingress auth first (headers), then HMAC on prompt callbacks, then parse
JSON.

| `answer.type` | When                                                |
| ------------- | --------------------------------------------------- |
| `option`      | Human tapped a button — `value` is the option label |
| `text`        | Free-text reply — `value` is the reply body         |

| `answer.origin`  | When                                                                             |
| ---------------- | -------------------------------------------------------------------------------- |
| `direct`         | Human answered on this channel (default when omitted on single send)             |
| `broadcast_sync` | Row closed by batch resolution on another channel — includes `source_channel_id` |

## Broadcast prompt batches

When a prompt is part of a multi-channel fan-out (`broadcast_batch_id` on the row),
the answer callback fires **once per batch** when the batch's `prompt_answer_mode`
rule is satisfied — not once per channel.

Resolved batch example:

```json
{
  "prompt_id": "#2",
  "channel_id": "slack-ops",
  "correlation_id": "deploy-42",
  "callback_data": { "build_id": 9182 },
  "text": "Approve production deploy?",
  "broadcast_batch_id": "brd_abc123",
  "broadcast_answer_mode": "first_answer",
  "broadcast_batch_status": "RESOLVED",
  "answering_channel_id": "telegram-alerts",
  "answer": {
    "type": "option",
    "value": "Approve",
    "user_id": 42,
    "username": "alice"
  },
  "answered_at": "2026-07-25T12:00:00.000Z"
}
```

| Field                    | Notes                                                                      |
| ------------------------ | -------------------------------------------------------------------------- |
| `broadcast_batch_id`     | Links all rows from one API fan-out (`brd_…`)                              |
| `broadcast_answer_mode`  | Snapshotted mode: `first_answer`, `all_answer_same`, `all_answer_majority` |
| `broadcast_batch_status` | `COLLECTING`, `RESOLVED`, `CONFLICT`, `EXPIRED`                            |
| `answering_channel_id`   | Channel where the decisive direct answer was recorded                      |

**No callback** when `all_answer_same` completes with disagreeing answers —
`broadcast_batch_status` becomes `CONFLICT`. See [Broadcast Groups](/guides/broadcast-groups)
for mode rules and [Prompts](/guides/prompts) for chat confirmations.

## Channel message callbacks (unsigned)

For `MESSAGE` channels with `callback_url`, inbound text becomes:

Greenlight also stores inbound rows in the message history table for operator
audit (see [Messages](/guides/messages)).

```json
{
  "type": "message.created",
  "platform": "slack",
  "channel_id": "ops-slack",
  "from": "alice",
  "text": "Looks good",
  "callback_data": {
    "tenant": "acme",
    "room": "support"
  }
}
```

Optional `callback_headers` on the MESSAGE channel authenticate the webhook.
Optional channel `callback_data` is static JSON merged into every forward.

These events are **not** signed. Retries use `CHANNEL_CALLBACK_MAX_RETRIES`
(default 3) and `CHANNEL_CALLBACK_RETRY_DELAY` seconds (default 5).

## Verification checklist

1. Read the raw request body bytes
2. Compute HMAC-SHA256 with `CALLBACK_SIGNING_SECRET`
3. Compare to the `sha256=` hex in `X-Signature` (timing-safe)
4. Reject mismatches with 401

See [Security](/guides/security) for SSRF protections on callback URLs.
