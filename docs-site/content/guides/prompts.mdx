# Prompts

Prompts are interactive questions delivered to a `PROMPT` channel.

Create prompts with `POST /v1/prompts/new` — the `/new` verb means **create a
durable resource**. For MESSAGE channel chat replies, use
`POST /v1/messages/send` instead.

## Create (`POST /v1/prompts/new`)

Send **`application/json`** or **`multipart/form-data`** to the same path.

### JSON body

| Field              | Type     | Default                     | Notes                                                                    |
| ------------------ | -------- | --------------------------- | ------------------------------------------------------------------------ |
| `channel_id`           | string   | `DEFAULT_PROMPT_CHANNEL_ID` | Single-channel send; mutually exclusive with `broadcast_group` / `broadcast_group_id` |
| `broadcast_group`      | object   | —                           | API-only ad-hoc fan-out: `channel_ids` + required `prompt_answer_mode` |
| `broadcast_group_id`   | string   | —                           | Enterprise: send to a saved [broadcast group](/guides/broadcast-groups)                 |
| `text`             | string   | —                           | Required, max 4096                                                       |
| `options`          | string[] | `[]`                        | Max 10 items (3 on WhatsApp/Messenger), each max 64 chars                |
| `allow_text`       | boolean  | `false`                     | Allow free-text replies                                                  |
| `callback_url`     | string   | —                           | Validated HTTP(S) URL                                                    |
| `correlation_id`   | string   | —                           | Short label echoed in answer callback (logs, dashboards)                 |
| `callback_data`    | object   | —                           | Optional JSON workflow state (max 8192 bytes), echoed in answer callback |
| `callback_headers` | object   | —                           | Optional outbound HTTP headers (max 4096 bytes); not returned on GET     |
| `ttl_sec`          | int      | `3600`                      | 0–604800 (7 days)                                                        |
| `media_url`        | string   | —                           | Remote attachment URL                                                    |
| `media_path`       | string   | —                           | Local path under `MEDIA_ALLOWED_DIR`                                     |

Provide **exactly one** send target: `channel_id`, `broadcast_group_id` (Enterprise),
or inline `broadcast_group` (API only — not available in the web UI). Community
rejects `broadcast_group_id` without an Enterprise license.

### Multipart form (file upload)

Use the same logical fields as form fields. Send the attachment as `file`.
`options` may be a JSON string. Do not combine `file` and `media_url`.

Only one media source is allowed among `media_url`, `media_path`, and upload
`file`.

Default content type for uploads is `image/jpeg`. Max size is governed by
`MAX_MEDIA_SIZE_MB` (default 2).

## Text replies

When `allow_text` is true, prompts include a **Type answer** button. The user taps it,
then sends any plain message — Greenlight records that message as the answer for that
prompt (no `ID:#n` prefix required). One armed text session per user per chat; tapping
Type answer on another prompt switches the target.

Power-user syntax is still supported:

```
ID:#1 my free-text answer
```

Also accepted: `ID:1 …`, `ID #1 …`, `ID-1 …` (case-insensitive). This overrides an
armed text session when both are active.

On WhatsApp and Messenger, `allow_text` reserves one button slot — use at most **two**
option labels (three buttons total including Type answer).

Greenlight records `answer.type = "text"` and posts a confirmation in the thread.

Prompts appear in chat with a **Prompt #n** title (matching the API id). After a
button tap or text reply, Greenlight posts a confirmation in the thread:

- First answer: `Recorded answer for ID:#2 Approve`
- Repeat tap on the same prompt: `Already answered for ID:#2: Approve` (no duplicate callback)
- Expired prompt: `Prompt expired for ID:#2`
- Batch resolved on another channel (sync-closed row): `Already answered on slack-ops: Approve`
- Batch decided (`first_answer` / unanimous): `Broadcast decided: Approve (answered on telegram-alerts)`
- Batch majority: `Majority decided: Approve`
- Batch conflict (`all_answer_same` split): `Prompt was not processed — channel answers did not agree.`

Arbitrary plain text on a PROMPT channel (without Type answer or `ID:#n`) is still
ignored — use a MESSAGE channel for free chat.

## Prompt ids

Each PROMPT channel has its own `#n` sequence (`telegram-prompts` #1, #2;
`slack-ops` also #1, #2). The number is scoped by `channel_id`, not globally
across the organization.

Use `correlation_id` for a short human-readable label (build id, ticket ref).
Use `callback_data` for arbitrary JSON workflow state your automation needs when
the answer callback fires — for example `{"build_id":9182,"step":"approve"}`.

## Broadcast answer modes

When sending to multiple PROMPT channels (inline `broadcast_group` or saved
`broadcast_group_id`), each row stores snapshotted `broadcast_answer_mode` from
the group's `prompt_answer_mode` at send time:

| Mode | API value | Resolution |
| ---- | --------- | ---------- |
| First answer | `first_answer` | First channel answer closes the batch; all channels notified |
| All same answer | `all_answer_same` | All channels must answer; unanimous → one callback; split → `CONFLICT`, no callback |
| Majority answer | `all_answer_majority` | Strict majority closes remaining channels; all channels notified |

## Two-layer status

**Per row** — `state`: `PENDING`, `ANSWERED`, `EXPIRED` (unchanged).

**Per batch** — `broadcast_batch_status` on rows sharing a `broadcast_batch_id`:

| Value | Meaning |
| ----- | ------- |
| `COLLECTING` | Batch not resolved yet |
| `RESOLVED` | Rule satisfied; callback fired when applicable |
| `CONFLICT` | `all_answer_same`: all answered but values disagreed |
| `EXPIRED` | Batch expired without resolution |

## Answer JSON

Direct answer on the answering channel:

```json
{ "type": "option", "value": "Approve", "origin": "direct" }
```

Sync-closed sibling row (batch resolution on another channel):

```json
{
  "type": "option",
  "value": "Approve",
  "origin": "broadcast_sync",
  "source_channel_id": "telegram-alerts"
}
```

`answered_by_*` fields apply only to direct rows. See [Callbacks](/guides/callbacks)
for batch callback payload fields.

## States (per row)

| State      | Meaning                       |
| ---------- | ----------------------------- |
| `PENDING`  | Waiting for an answer         |
| `ANSWERED` | Button or text reply recorded |
| `EXPIRED`  | TTL elapsed                   |

Background expiry runs periodically. `CLEAN_ON_BOOT` can clear stale state on
startup.

## List

```bash
GET /v1/prompts?state=pending
GET /v1/prompts?state=all&limit=100
GET /v1/prompts?channel_id=telegram-prompts&state=pending
```

`state`: `pending` (default) \| `answered` \| `expired` \| `all`. `limit`: 1–200 (default 50).
Optional `channel_id` filters to one PROMPT channel.

## Fetch by id

IDs look like `#1` per channel — URL-encode the `#` as `%23` and pass
`channel_id`:

```bash
GET /v1/prompts/%231?channel_id=telegram-prompts
```

`channel_id` is required. Without it the API returns 400.

Multi-channel sends set a shared `broadcast_batch_id` on each row. Filter with
`GET /v1/prompts?broadcast_batch_id=brd_…`. Enterprise group sends also set
`broadcast_group_id`. See [Broadcast Groups](/guides/broadcast-groups).

Prompt ids are not access control — set `USE_AUTH=true` in production and protect
the Agent API with scoped API keys.
